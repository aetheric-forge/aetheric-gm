# v0.4 — session notebooks

The first slice is one continuous Markdown notebook per campaign session. A GM prepares a few
ideas, writes during play, and later polishes the same document into a narrative. No mandatory
prep/live/recap sections are imposed.

## First slice: Story 22

- Campaign-scoped session index with title/body search and new notebooks.
- Optional planned date and draft/running/completed states, with explicit reopening allowed.
- Write and preview modes using the existing Markdown renderer.
- Autosave after a short pause, explicit Save now, and visible save/conflict/error status.
- Per-user, per-session browser-tab draft recovery after refresh. Browser storage is temporary;
  only Saved confirms database persistence. Closing the tab may remove its recovery copy.
- Append-only revisions including title, date, lifecycle state, author subject ID, and body.
- Inspect and restore an old revision as a new revision, retaining the polished and original text.
- Insert stable campaign links to characters, NPCs, people, factions, and places.

## Second slice: Story 23 — session continuity

Create next session from a saved notebook. Carry selected source text, use the entire source as
an editable starting point, or leave the next document blank. Unresolved threads remain prose;
there is no imposed checklist or required heading structure.

The next notebook starts as Draft with a new ID and its own history. It retains an immutable
source session ID and source revision, scoped to the same campaign. Previous/following links
connect the notebooks; source-revision preview preserves what the GM was referring to even
after later edits. More than one following session is allowed for branching preparation.

Existing notebooks migrate additively to schema version 2 with no continuation relationship.
The upgrade is transactional and safe to repeat. Creation does not mutate source status, notes,
or history. Pending edits in the current notebook must save successfully before navigating to
Create next session. The carry-forward form requires explicit creation and warns before leaving
with unsaved entries; it is not autosaved until it becomes a notebook.

### QA checkpoint: continuity

1. Open an existing notebook, edit it, and immediately choose Create next session. Verify the
   saved source shown on the next page includes the edit.
2. Select a paragraph in Previous notes, choose Carry selected text, and add an unresolved thread.
   Give it a title/date and create. Expect a new Draft containing only the chosen/edited notes.
3. Follow the previous-session link; verify the source is unchanged and links forward to the new
   session. Rename the source, then revisit the child: the link uses the new title, while Read the
   source revision still shows the originally referenced text.
4. Create another continuation with blank notes. Also try Use entire source notebook, edit it
   down, and verify both following sessions remain listed.
5. Try an empty title: expect validation with notes retained. Cancel navigation with unsaved
   carry-forward notes: expect to remain on the form. On iPad, verify text selection and buttons.
6. Recheck the earlier notebook QA: stale-tab conflict, refresh recovery, preview, and restoring
   a revision without losing newer history.

## Integration direction

Runtime owns Conversation and TableTop abstractions. Future session associations will reference
provider/scope/external IDs, leaving vendor SDKs, subscribers, and API forwarders in adapters.
Conversation may supply Slack threads and messages; TableTop may supply Owlbear room/scene context.
Imported material must preserve origin/event IDs and authorship separately from notebook edits.
Outbound publication requires an explicit user action. These integrations are not implemented in
this first slice and the notebook does not require an external connection.

## Persistence and validation

Session IDs and campaign IDs are stable. Every save compares the head revision, updates the head,
and inserts a revision in one SQLite transaction. A stale tab cannot overwrite a newer head.
History restoration uses the current head's revision, preserving all intervening versions.
The initial additive session schema has a separate version marker; existing GM tables are unchanged.
This does not replace the outstanding migration work for older repositories.

Automated coverage includes lifecycle/persistence, revision restore, stale-write conflicts,
campaign isolation, missing campaigns, duplicate creation, input validation, and browser-draft
save/recovery races. The JavaScript test harness uses a simulated DOM and storage; it does not
replace authenticated browser testing.

## Local smoke test

1. Open an existing campaign and choose Open sessions. Create a notebook.
2. Write Markdown and a campaign link; wait for Saved, then refresh and preview.
3. Change Draft to Running, take notes, then mark Completed and polish the narrative.
4. Open revision history, inspect the original, and restore it; verify later revisions remain.
5. Open the same notebook in two tabs. Save in one, then edit the stale tab: expect a conflict.
6. In the stale tab, load latest and recover its draft. Review and save explicitly.
7. Refresh with an unsaved draft: recover or discard it. Test with browser storage blocked too.

Encounters, initiative, combat automation, and live Slack/Owlbear adapters remain separate work.
Deployment automation is deferred to v1.0. This document does not declare v0.4 released.
