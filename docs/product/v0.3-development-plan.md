# v0.3 development plan

Version 0.3 begins with a deliberately small stabilization and design gate, followed by one complete NPC-catalog slice. This plan turns the code review following v0.2 into an ordered sequence; it does not expand the milestone into encounters, initiative, or combat automation.

## Phase 0 — stabilize the v0.2 baseline

Before introducing new persistence or UI behavior:

1. Update the SQLite dependency chain to remove the reported high-severity `SQLitePCLRaw.lib.e_sqlite3` vulnerability, then restore, build, and run all tests.
2. Perform a browser smoke test of sign-in and sign-out, campaign lifecycle, public and private rules-package installation, character creation and persistence, character-sheet rolls, inline rules rolls, keyboard navigation, and reduced-motion behavior.
3. Add one automated browser happy path covering campaign creation through a persisted character roll.
4. Add a root README describing prerequisites, Keycloak and user-secret configuration, local startup, rules-package test data, and build/test commands.
5. Add continuous integration for restore, build, tests, and vulnerable-package detection.

The phase is complete when the dependency audit is clean, the automated suite passes, and the documented smoke test has no release-blocking defects.

## Phase 1 — define the NPC domain contract

Write and review a compact architecture decision before building the UI. It must define:

- campaign-owned NPC identity and lifecycle;
- an optional reference to the exact source ruleset ID, version, record type, and record key;
- which source values are copied into campaign ownership and which remain resolved package content;
- editable name, notes, tags, role, location, disposition, and status;
- typed current resources and their reset or adjustment semantics;
- traits and rollable actions, including labels, dice expressions, modifiers, advantage state, and NPC roll context;
- behavior when a source package or record is unavailable;
- search and filter semantics; and
- the accessibility vocabulary for catalog, inspection, editing, and actions.

The contract must preserve the boundary in Story 18: package records are immutable, campaign NPCs have independent identity and mutable state, and changing package labels or ordering cannot overwrite campaign-owned state.

## Phase 2 — establish schema evolution

Add a small ordered SQLite migration runner and a schema-version table before adding NPC tables. Replace repository-specific ad hoc schema evolution incrementally; existing initialization behavior must remain compatible with current local databases.

The initial NPC migration should support campaign ownership, source provenance, editable metadata, resources, actions, and indexed catalog queries. Storage details must remain behind Core repository ports.

## Phase 3 — deliver Story 18 vertically

Implement the smallest complete path in this order:

1. **Core:** introduce the NPC aggregate, source reference, resource and action value types, invariants, and `INpcRepository`.
2. **Infrastructure:** persist and query campaign NPCs in SQLite, including campaign, name, source, tag, role, location, and status filters.
3. **Rules integration:** discover compatible NPC records only from the campaign's exact selected ruleset ID and version.
4. **Copy workflow:** create a new campaign-owned NPC from a package record without making the package record mutable.
5. **Web:** add a dedicated campaign NPC route with catalog search and filters, clear source ownership, inspection, copy, and campaign-NPC editing.
6. **Live play:** send NPC actions through the shared dice tray with a human-readable label and NPC context.

Keep NPC coordination outside the existing campaign home component. Extract focused application services or components where campaign, rules-package, and profile orchestration would otherwise accumulate in Razor pages.

## Phase 4 — verification and release decision

Translate every Story 18 acceptance criterion into domain, adapter, component, or browser coverage. Pay particular attention to:

- exact ruleset-version isolation;
- independent state for multiple NPCs copied from one source;
- readable campaign data when source content disappears;
- immutable package records;
- persistence and indexed filtering;
- dice history retaining NPC context; and
- keyboard and assistive-technology operation.

After Story 18 is demonstrated end to end, review user feedback and select any remaining v0.3 scope explicitly. Encounter composition, initiative, combat automation, maps, and procedural generation remain uncommitted.

## First implementation ticket

**Stabilize v0.2 and define the NPC domain contract.** Complete Phase 0, then produce the Phase 1 architecture decision. The first feature ticket after that gate is: list package NPCs, copy one into a campaign, edit and persist it, and roll one action.
